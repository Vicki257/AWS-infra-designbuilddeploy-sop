# Phase 1　设计

**目标**：让「构筑时抄的那份文档」是正确的、完整的、且定义了**最终状态**。

| Step | 标题 | 担当 |
|---|---|---|
| 1-1 | 方式设计书的取得 | 人 |
| 1-2 | **G1 文档间一致性检查** | **AI** |
| 1-3 | **G2 设计实在性审查** | **AI** |
| 1-4 | 依赖关系登记 | AI → 人确认 |
| 1-5 | 环境设计书的确定 | 人 |
| 1-6 | **最终状态定义书的作成** | AI + 人 |

## Step 1-2　G1　文档间一致性检查

**担当**：AI　**产出**：矛盾一览

### 为什么

**这一步是整套 SOP 里投入产出比最高的一步。** 5 分钟，能挡住大部分「和设计书不符」的指摘。

### 手顺

**① 人把两份文档贴给 AI**（Excel 就按 sheet 分别贴文本）

**② AI 使用 `docs/92-prompts.md` 的 A-1 模板**

**③ AI 输出矛盾一览**

```
| # | 项目 | 方式设计书的记载 | 环境设计书的记载 | 判定 |
```

判定三种：
- **矛盾**：两者定义了不同的值
- **欠落**：方式设计书有，环境设计书没有
- **过剰**：环境设计书有，但方式设计书找不到根据

**④ 人逐行处理**（AI 不做这个判断）

| 判定 | 处理 |
|---|---|
| 矛盾 | **以方式设计书为准**修正环境设计书。方式设计书本身有问题时先改上位（需审查） |
| 欠落 | 补进环境设计书 |
| 过剰 | 删除，或向上位确认是否需要 |

### 必须重点对照的项目

- 安全组的**全部规则**（种别・端口・来源）
- 负载均衡器的**监听器构成**（协议・端口）
- 中间件的**版本**
- 健康检查的**路径与协议**
- **运行调度**与各种窗口（备份・维护）
- 加密的有无
- 冗余构成（Multi-AZ 等）

### 验收基准

- [ ] 矛盾一览的**所有行**都已处理
- [ ] 处理结果已反映进环境设计书
- [ ] 「过剰」项目全部已删除或已向上位确认

## Step 1-3　G2　设计实在性审查

**担当**：AI　**产出**：指摘一览

### 为什么

设计书里「写错了但没人发现」的东西，会原样变成实装。
典型：不存在的中间件版本号、互不兼容的组合、矛盾的时刻。

### 手顺

**① AI 使用 `docs/92-prompts.md` 的 A-2 模板**

**② AI 输出指摘一览**

```
| # | 位置 | 记载内容 | 指摘 | 根据 | 重要度 |
```

审查观点：
1. **实在性** — 软件版本 / 实例类型 / 引擎版本是否真实存在，该区域是否可用
2. **组合妥当性** — 中间件间的兼容性、OS 与中间件的对应
3. **数值整合性** — 时刻・调度的矛盾、容量・阈值的现实性
4. **记载欠落** — 生产运用必需但没写的项目

**③ 人处理重要度「高」的全部项目**

### 验收基准

- [ ] 重要度「高」的指摘全部解消，或已向上位确认
- [ ] AI 标记为「要确认」的项目已确认

## Step 1-4　依赖关系登记

**担当**：AI 抽出 → 人确认　**产出**：`workspace/DEPENDENCIES.md`

### 为什么

**「改了 A，依赖 A 的 B 没人回头查」**是第二常见的事故。
典型：运行时间改了，但 RDS 备份窗口没跟着改 → 备份永远落在停机时段，**一次都没执行过**。

### 手顺

**① AI 使用 `docs/92-prompts.md` 的 A-3 模板抽出依赖**

**② 输出到 `workspace/DEPENDENCIES.md`**

最低限必须包含的依赖（AI 要主动检查这些有没有被漏）：

| # | 变更的值 | 受影响的值 | 理由 |
|---|---|---|---|
| 1 | RDS 停止时刻 | PreferredBackupWindow | 停止中不执行备份 |
| 2 | RDS 停止时刻 | PreferredMaintenanceWindow | 同上 |
| 3 | 运行调度 | 告警的 TreatMissingData | 停止中指标缺损会误报 |
| 4 | **证书取得** | **ALB 监听器构成** | HTTPS 追加・HTTP 撤去 |
| 5 | **证书取得** | **ELB SG 的入站** | 80 变得不需要 |
| 6 | **证书取得** | **开闭局处理的对象 ARN** | 监听器换了，Lambda 要跟着换 |
| 7 | 公开路径 | 健康检查路径 | |
| 8 | 公开路径 | 反向代理设定（httpd） | |
| 9 | 公开路径 | Outputs 的 URL | |
| 10 | 实例类型 | 成本试算 | |

**③ 人确认无遗漏**

### 验收基准

- [ ] `workspace/DEPENDENCIES.md` 已作成
- [ ] 上表 10 项全部已包含（不适用的项目明确标记「不适用」）

## Step 1-6　最终状态定义书的作成

**担当**：AI 起草 → 人确定　**产出**：`workspace/FINAL_STATE.md`

### 为什么

**这是防止「加了新的，旧的没删」的核心。**

设计书写的是最终状态，但构筑是**分阶段**的。
阶段之间的差分（暂定配置）不被管理，就会残留到交付。

### 手顺

**① AI 从确定版环境设计书生成「1. 最终状态」**

每个表的**末尾必须写**：

```
（上記以外は存在しないこと）
```

**这一句是整份文档的核心。** 没有它，AI 和人都无法检出「多余的东西」。

**② 人定义「2. 构筑阶段与暂定状态」**

```
| Phase | 条件 | 暂定允许的状态 | 撤去时机(Gate) |
|---|---|---|---|
| P1 疎通确认 | 证书未取得 | ALB HTTP:80 监听器 / ELB SG 80 | G5 |
| P2 问题解析 | 解析中 | EC2 SG 80 ← 0.0.0.0/0 | G6 |
```

**③ 同时登记进 `workspace/TEMP_SETTINGS.md`**（暂定设定台账）

### 验收基准

- [ ] `workspace/FINAL_STATE.md` 已作成
- [ ] **每个表的末尾都有「（上記以外は存在しないこと）」**
- [ ] 暂定状态全部登记进 `TEMP_SETTINGS.md`，且都有撤去条件和期限(Gate)
